# Module Log: Settings

> Session-by-session implementation history for `Modules/Settings/**` — includes pure configuration/reference data (Company Profile, Currencies, UoM, Document Numbering, Approval Matrix), the read-only Audit Log browser, and the System Administration group (`Setting_Modules`/`Setting_Menus`, physically coded here per [../AGENTS.md](../../AGENTS.md)). Cross-cutting architecture decisions/conventions live in [../plan.md](../plan.md).

## Phase E: rest of the Settings module implemented
Only `Setting_AuditLogs` existed before this session (created early, out of order, because `Shared/Logging/AuditLogService` needed the table from day one — see [identity.md](identity.md)) — the other 8 tables/entities/controllers below are new.

- **New shared building blocks** (so simple ref-data entities don't need bespoke Repository/UseCase classes):
  - `Shared/Persistence/GenericRepository<TEntity>` — a concrete, DI-instantiable subclass of the existing abstract `Repository<TEntity>` (the base class alone can't be registered/resolved by the container since it has no public constructor of its own accessible generically).
  - `Shared/Common/CrudUseCase<TEntity>` — wraps a `GenericRepository<TEntity>` with audit logging (`Create`/`Update`/`SoftDelete`) and takes the target table name as a constructor string, so `IAuditLogService.LogAsync` calls stay correct per entity without per-entity boilerplate.
  - This is the concrete implementation of the "Simple reference data can skip a bespoke UseCase" rule stated in `AGENTS.md`/[../plan.md](../plan.md) — controllers for `Currency`/`UnitOfMeasurement`/`Incoterm`/`Port`/`Warehouse`/`CompanyProfile`/`ApprovalMatrix` now just inject `CrudUseCase<TEntity>` directly.
- **New tables** (`Scripts/Settings/0003`–`0010`, all idempotent `IF NOT EXISTS`): `Setting_CompanyProfile` (singleton, always `Id=1`), `Setting_Warehouses`, `Setting_Currencies`, `Setting_UnitsOfMeasurement`, `Setting_Incoterms`, `Setting_Ports`, `Setting_DocumentNumberings`, `Setting_ApprovalMatrices` (FKs to `Setting_Currencies` and `Identity_Roles`). `0012_Seed_CompanyProfile.sql` inserts the one default row.
- **`usp_Setting_DocumentNumbering_GetNext`** (`Scripts/Settings/Procedures/0011_...sql`): uses `SELECT ... WITH (UPDLOCK, HOLDLOCK)` inside an explicit transaction to make next-number generation concurrency-safe (two simultaneous requests for the same `DocumentType` can never get the same number). Handles `ResetPeriod` (`Never`/`Yearly`/`Monthly`) and a `{Prefix}{Number}{Suffix}{Year}{Month}` `FormatTemplate` token replacement, returning both the raw `CurrentNumber` and the `FormattedNumber`.
- **Entities** (`Modules/Settings/Entities/*.cs`): `CompanyProfile`, `Warehouse`, `Currency`, `UnitOfMeasurement`, `Incoterm`, `Port`, `DocumentNumbering`, `ApprovalMatrix` — DataAnnotations validation directly on entity properties (no separate DTOs for these simple ref-data entities, a deliberate simplification vs. Identity's Entity/Dto split, acceptable since there's no business logic to hide from the wire format).
- **`DocumentNumberingRepository`/`IDocumentNumberingRepository`** (bespoke, extends `GenericRepository<DocumentNumbering>`): adds `GetNextAsync(documentType)` calling the stored proc via `QuerySingleStoredProcedureAsync<NextDocumentNumberResult>`. `DocumentNumberGeneratorService` wraps it so future modules (Sales/Export Documentation) depend on the service, not the repository, directly.
- **`AuditLogQuery`** (`Modules/Settings/Queries/AuditLogQuery.cs`): paged + optional `TableName`/`Action` filters, `COUNT(*) OVER()` window function for total count (same pattern as `RoleListQuery`).
- **Controllers** (`Modules/Settings/Controllers/`): `CompanyProfileController` (Get/Update only — singleton, no Create/Delete exposed), `WarehousesController`, `CurrenciesController`, `UnitsOfMeasurementController`, `IncotermsController`, `PortsController`, `ApprovalMatricesController`, `DocumentNumberingsController` (adds `POST {documentType}/next` to reserve the next number), `AuditLogsController` (read-only). All use `[Authorize(Policy = "Settings_View")]` for reads and `"Settings_Manage"` for writes (`AuditLogsController` uses `"AuditLog_View"`) — these permission codes already existed from Identity's seed data, no new permissions needed.
- **`SettingsModuleExtensions.AddSettingsModule()`**: registers a `GenericRepository<T>` + `CrudUseCase<T>` pair per simple entity, plus `IDocumentNumberingRepository`/`DocumentNumberGeneratorService`/`AuditLogQuery`; called from `Program.cs` alongside `AddIdentityModule()`.
- Validated: `dotnet build Sugentra.ERP.sln` — 0 warnings/errors. `dotnet test` — 1/1 passing (`ModuleBoundaryTests` confirms no `Modules.Settings` → `Modules.Identity` namespace leakage). Migrator applied all 9 new scripts successfully against the live DB (confirmed "Upgrade successful").
- **Not yet done at this point:** no DTOs/paging for the simple ref-data list endpoints (`GetAll` returns the full unpaged list — acceptable for reference data that's expected to stay small, revisit if any of these tables grow large); `ApprovalMatrix` has no workflow execution engine (metadata storage only, as scoped in Phase 1); Settings entities have no dedicated unit tests yet.

## Decision: post-login UI navigation — module hub pattern
Discussed and decided the UI navigation model ahead of building the Master Data UI further, so future frontend work doesn't drift:

- **Chosen pattern:** post-login landing page = a grid of module boxes (icon/image + name), filtered to only the modules the current user has any permission in. Clicking a module box navigates into that module's own workspace/sidebar (same `SidebarMenuViewComponent` mechanism, scoped to that module). This is the standard "app launcher" pattern (Odoo apps grid / SAP Fiori Launchpad style), chosen over a flat single-sidebar-with-everything because it scales better as more of the ~13 planned modules get built out. See [ui.md](ui.md) for the frontend rendering side of this decision.
- **Still plain MVC** — not a SPA/AJAX rewrite. Considered making the whole UI call the API directly from the browser (so Network tab shows API calls) but rejected: it would require exposing the JWT to client-side JS (currently deliberately kept server-side only, in the auth cookie), CORS setup, and rewriting every Razor view as client-rendered — high effort/security-risk for low payoff at this stage.
- **New API built to support the hub:** `Setting_Modules` table + `Module` entity/`ModulesController` (`GET/POST/PUT/DELETE /api/settings/modules`), permissions `Module_View`/`Module_Manage`. Columns: `Code`, `Name`, `Icon` (font icon class, for compact contexts like the hub grid and sidebar), `ImageUrl` (banner image, intended for the module's own detail/landing page header), `Route`, `SortOrder`, `IsActive`.
  - Files: `Scripts/Settings/0014_Setting_Modules.sql` (table + seed of all 13 planned module codes), `Scripts/Identity/0014_Seed_ModulePermissions.sql` (permission seed + role grants), `Modules/Settings/Entities/Module.cs`, `Modules/Settings/Controllers/ModulesController.cs`, registered in `SettingsModuleExtensions.cs`. Follows the exact same `GenericRepository<T>`/`CrudUseCase<T>` pattern as `Currency`/`Warehouse`.
  - **Note:** the entity is named `Module` (not `AppModule`/`SystemModule`) — this collides by name (not namespace) with `System.Reflection.Module`; an alias (`using Module = Sugentra.ERP.Api.Modules.Settings.Entities.Module;`) is used in files that need disambiguation.
- **Deliberately deferred at this point:** `Identity_Permissions.Module` is a free-text string column, not linked via FK to `Setting_Modules.Id`. The intended design (still not implemented as of the latest session): add `Identity_Permissions.ModuleId BIGINT FK → Setting_Modules(Id)`, backfill from the existing string values, and use it to drive "which module boxes does this user see in the hub" — no separate module-access table needed.

- **Sidebar fully migrated off the static `SidebarMenuDefinition.cs`** (file deleted) onto `Setting_Menus`/`Setting_Modules`:
  - New API endpoint `GET /api/settings/menus/active` (any authenticated user, same pattern as `GET /api/settings/modules/active`) — `MenuQuery.GetActiveForPermissionCodesAsync` builds a module→menu tree filtered by the caller's JWT `permission` claims, with **orphan promotion**: if a node's parent got filtered out by permission, the node is promoted to top-level instead of being silently dropped.
  - Frontend consumption (`SidebarMenuViewComponent`, `WorkspaceController`, `_MenuNode.cshtml`) documented in [ui.md](ui.md).
  - **`HasWorkspace` reuses `Setting_Modules.Route`** (non-null ⇒ has its own module landing/workspace page with "Back to Modules"; null ⇒ renders as a flat top-level sidebar group) — avoided adding a redundant new column.
  - Three system-only module rows added to seed a home for previously module-less menu items: `SystemAdministration` (owns Modules + Menus), `AuditLog`, `UIKit` (`Scripts/Settings/0021_Setting_Modules_SystemGroups.sql`), all with matching `Setting_Menus` rows seeded in `0022_Seed_Setting_Menus.sql`.
  - **Gotcha discovered and fixed**: the dashboard hub's `ModuleQuery.GetActiveForPermissionCodesAsync` matches `Identity_Permissions.Module` against `Setting_Modules.Code` — the `Module_View`/`Menu_View`/`AuditLog_View` permissions were still seeded with the old `Module = 'Settings'` value, so the 3 new modules never appeared as dashboard tiles even once activated. Fixed via `Scripts/Identity/0016_Fix_SystemModule_PermissionMapping.sql`: reassigned those permissions' `Module` column to the correct new codes, and added a dedicated `UIKit_View` permission (granted to all roles) since the "Tables" menu item had no permission at all and could never satisfy the match. **Lesson: whenever a menu item moves to a different module, its permission's `Module` column must move with it, or the dashboard hub tile silently never shows up** — this is the exact `ModuleId` FK gap flagged above; still not fixed structurally, only patched with correct string values.
  - The 3 system modules were then given real workspace routes (`Scripts/Settings/0024_Setting_Modules_SystemGroup_Routes.sql`, `/Workspace/Index/{Code}`) and activated (`0023_Activate_SystemGroups.sql`) so they show up and work exactly like Identity/MasterData/Settings.
- **Reminder for the user, given each time permissions changed**: permissions are resolved once at login and baked into the JWT as claims (`PermissionResolverService`) — any permission/module reassignment requires logging out and back in before it takes effect; the DB alone updating is not enough.
- Validated: `dotnet build Sugentra.ERP.sln` — 0 warnings/errors after every change; `ModuleBoundaryTests` (NetArchTest) still green after adding `Menu`/`MenuQuery`/`MenusController` inside `Modules/Settings/**`. ## Audit Log Detail page polish — bug fix, diff highlighting, First/Prev/Next/Last navigation
- **Fixed 500 on Detail click**: `AuditLogQuery._byIdSql` selected 11 columns but Dapper materializes `AuditLogRow` (a private record with a `TotalCount` 12th param) by matching a constructor to the *exact* resultset column set — since `TotalCount` wasn't projected by `_byIdSql` (only `_pagedSql` has `COUNT(*) OVER()`), Dapper couldn't find a matching constructor and threw `InvalidOperationException`. Fixed by adding `0 AS TotalCount` to `_byIdSql`. **Lesson: any query sharing a Dapper row-mapping record with another query must project every column that record's constructor expects, even if the value is a dummy/default.**
- **`Views/AuditLogs/Detail.cshtml` rebuilt several times** based on iterative user feedback; final shape: identity card ("Audit Log Detail" as `card-header`, "Entry #Id" + bold field labels in the body) separate from two side-by-side Old/New Value cards (colored headers: `bg-label-danger`/`bg-label-success`, no height cap — grows to fit content, `pt-*` top padding so JSON doesn't touch the header rule).
- **Line-level diff highlighting**: both Old/New JSON values are pretty-printed then split into lines; lines that differ by index between the two sides get `bg-warning-subtle` applied to both. Rendered via a `BuildDiffHtml` helper returning `IHtmlContent` (built with `StringBuilder` + `Html.Raw`, values `HtmlEncode`d) — **not** a `@for` loop directly inside `<pre>`, because Razor renders the template's own whitespace/newlines as literal output, which was making every JSON line render double-spaced.
- **First/Previous/Next/Last navigation**: new API endpoint `GET /api/settings/audit-logs/{id}/adjacent` → `AuditLogQuery.GetAdjacentAsync` (new `AuditLogAdjacentDto(PreviousId, NextId, FirstId, LastId)`), single SQL query using correlated `MAX/MIN(Id) WHERE ChangedAt </> c.ChangedAt` for prev/next and a `TOP 1 ... ORDER BY ChangedAt ASC/DESC` for first/last (ordering matches the list's default `ChangedAt DESC` sort, not raw `Id`). UI `AuditLogsController.Detail` fetches this alongside the entry and exposes `ViewBag.PreviousId/NextId/FirstId/LastId`; buttons auto-disable when no adjacent entry exists.
- **Button styling iterated to**: square `btn-icon` buttons (not Bootstrap `pagination`/`page-link` circles) using the same `&laquo;/&lsaquo;/&rsaquo;/&raquo;` glyphs as `_PagingFooter.cshtml` (not remix-icon arrows) for First/Prev/Next/Last (`btn-label-secondary`), plus Refresh (`btn-label-dark`) and an icon-only "Back to List" (`btn-label-dark`) — all with Bootstrap tooltips (`data-bs-toggle="tooltip"`, globally initialized by `main.js`, no extra script needed). The header row (breadcrumb + these buttons) is a single `d-flex justify-content-between` row so they sit flush with the breadcrumb. The old text "Back to List" button at the bottom of the page was removed in favor of the icon button in the header.

- **Quill/table HTML corruption bug (root cause + final fix, `Views/EmailTemplates/Edit.cshtml`)**: Quill parses whatever HTML is loaded into it into its own internal Delta model and re-renders from that model — this round-trip has no concept of `<table>` layout, so it silently mangles table-based email HTML (logo/layout broken), and originally corrupted the *saved* `BodyHtml` even when a user opened Edit and clicked Save without changing anything (submit handler blindly read Quill's already-mangled `root.innerHTML`).
  - Rejected fix #1: gate saving on a `text-change`/`source === 'user'` flag so an untouched Save falls back to the pristine original HTML — fixed the "save without editing" case but real WYSIWYG edits still got mangled going forward.
  - Rejected fix #2: force table-based templates into read-only Quill + "View HTML"-only editing — technically safe, but explicitly rejected by the user ("breaks the dynamic function") since non-IT staff need to edit these templates visually, not via raw HTML source.
  - **Final fix**: server-side detection `isTableBased = /<table/i.test(originalBodyHtml)` decides the editing strategy per template. Non-table templates keep the normal Quill WYSIWYG editor unchanged. Table-based templates use a **native `contenteditable="true"` div** directly over the raw HTML instead of Quill — native contenteditable only mutates the DOM nodes the user actually interacts with (typing/deleting text) and never reparses/rebuilds the whole tree the way Quill's Delta round-trip does, so the table skeleton survives real edits. A `getEditorHtml()`/`setEditorHtml(html)` pair abstracts over both cases (Quill vs. plain div) so the View HTML toggle/Save/Preview logic doesn't need to branch. A `.raw-html-editor` CSS class gives the contenteditable div a Quill-like bordered/padded look, and a `#tableBasedHint` note explains the table shouldn't be deleted/restructured.

## Company Profile: multi-variant Logo/Icon fields + generic reusable upload service
- **6 image variant columns added to `Setting_CompanyProfile`** (`0041_Add_CompanyProfile_IconUrl.sql`, `0042_Add_CompanyProfile_Logo_Icon_Variants.sql`, both applied): `LogoUrl` (Logo/Light — the one actually used app-wide as the displayed logo in navbar/sidebar/login pages), `LogoDarkUrl`, `LogoSquareUrl`, `IconUrl` (Icon/Default), `IconLightUrl`, `IconDarkUrl`. All `NVARCHAR(500) NULL`, mirrored on both the API entity (`Modules/Settings/Entities/CompanyProfile.cs`) and UI model (`Models/Settings/CompanyProfile.cs`).
- **New generic, cross-module file upload service** (not Settings-specific, lives under `Shared/**` per the module-isolation exemption for shared building blocks — first consumer is Company Profile, but any module can reuse it):
  - `Scripts/Shared/0001_Shared_Uploads.sql` (applied) — one `Shared_Uploads` table for every upload category: `Category`, `EntityType`/`EntityId` (nullable, for tagging which record an upload belongs to — **not currently populated** by the Company Profile flow, a known gap), `FileName`/`StoredFileName`/`Extension`/`ContentType`/`SizeBytes`/`Url`/`StoragePath`/`StorageProvider`, `Width`/`Height`/`DurationSeconds` (reserved, unused so far), `IsPublic`, `Checksum` (reserved, unused so far), plus standard audit columns.
  - `Shared/Uploads/UploadCategories.cs` — central registry of per-category rules (`AllowedExtensions`, `MaxSizeBytes`, `IsPublic`) enforced server-side so clients can only pick a category, not loosen limits. `company-logos`: jpg/jpeg/png/webp, 2MB, public (SVG deliberately excluded — stored-XSS risk via embedded `<script>`). `documents`: pdf/doc/docx/xls/xlsx, 10MB, private. `videos`: mp4/mov, 100MB, private.
  - `Shared/Uploads/FileStorageService.cs` — validates size/extension, then **magic-byte signature check** (first bytes vs. known format signatures) so a renamed malicious file can't slip past extension-only validation; saves to `wwwroot/{Uploads:RootFolder}/{category}/{guid}.{ext}` (root folder name configurable via `appsettings.json` `Uploads:RootFolder`, defaults to `"uploads"` if unset — was hardcoded originally, made configurable per user request), records metadata via `GenericRepository<UploadFile>`.
  - **Replace-cleans-up-old-file support**: `SaveAsync` takes an optional `replaceUrl` — after the new file is saved, if `replaceUrl` was given it looks up the `Shared_Uploads` row with that `Url`, deletes its physical file, and soft-deletes the row. This prevents orphaned files/rows accumulating every time a user re-uploads a logo.
