# Frontend Log: Sugentra.ERP.UI (shared shell)

> Session-by-session implementation history for the `Sugentra.ERP.UI` MVC project's **shared/cross-module infrastructure** (layout, sidebar, dashboard/module hub, branding, login page). Per-module CRUD page details that are truly specific to one module (e.g. Users list polish) are logged in that module's own file ([identity.md](identity.md), [settings.md](settings.md), [master-data.md](master-data.md)). ## Phase H: Sugentra.ERP.UI — full ASP.NET Core MVC frontend
User approved building a complete web UI in the same solution, reusing a supplied Bootstrap 5 admin theme (`templates/AspnetCoreMvcFull/`, left untouched per instruction) rather than a separate repo/project family.

- **New project `src/Sugentra.ERP.UI/Sugentra.ERP.UI.csproj`** (net8.0, ASP.NET Core MVC — Controllers/Views, not Razor Pages), added to `Sugentra.ERP.sln`.
- **Auth**: cookie authentication (`CookieAuthenticationDefaults`) storing the API's JWT access token, refresh token, expiry and `"permission"` claims directly on the cookie's `ClaimsIdentity` at login (`AccountController.Login`) — no server-side session store. Global fallback policy `RequireAuthenticatedUser()`; only `Account/Login` and `Account/AccessDenied` are `[AllowAnonymous]`.
- **Permission-based authorization mirrored from the API**: `Auth/PermissionAuthorization.cs` reimplements `PermissionPolicyProvider`/`PermissionAuthorizationHandler` UI-side so `[Authorize(Policy = "Xxx_View")]` on controllers works identically, driven by the `permission` claims copied from the JWT. `ClaimsPrincipalExtensions.HasPermission()` used in views to conditionally show Create/Edit/Delete buttons and sidebar items.
- **API integration**: typed `ApiClient` (`AddHttpClient<ApiClient>()`, base URL from `Api:BaseUrl` in `appsettings.json`, matching the API's `launchSettings.json` port) attaches the bearer token from the current user's claims on every call, deserializes the API's `ApiResponse<T>`/`PagedResult<T>` envelope with `PropertyNameCaseInsensitive = true` (API returns camelCase JSON, UI models are PascalCase). All error/success messages shown to the user come directly from the API's `Message` field — no hardcoded UI copy for API outcomes.
- **UI theme**: only `wwwroot/` assets, the `Sections/_Styles.cshtml` / `_Scripts.cshtml` / `_ScriptsIncludes.cshtml` include-partials, and the login page markup were reused from the template; the template's own `_Variables.cshtml`/`_NavbarPartial.cshtml`/`_Footer.cshtml` (full of Pixinvent marketing/license `TempData` vars) were deliberately NOT copied — replaced with a minimal custom `_Layout.cshtml`/`_LoginLayout.cshtml`, `NavbarViewComponent`, and `SidebarMenuViewComponent`.
- **Sidebar** (`Models/Layout/SidebarMenuDefinition.cs`, later deleted — see "fully dynamic Menus/sidebar" below) initially a static, permission-filtered definition covering every module: Identity (Users, Roles, Permissions), Master Data (Business Partners, Items, Bill of Materials, Price Lists), Settings (Currencies, Units of Measurement), Audit Log.
- **Pages built, one controller+view set per module**: `AccountController` (Login/Logout/AccessDenied), `DashboardController`, `UsersController` (+ Unlock/Deactivate actions), `RolesController` (+ permission assign/revoke), `PermissionsController` (read-only), `BusinessPartnersController`, `ItemsController`, `PriceListsController`, `BillOfMaterialsController` (composite header+dynamic component lines), `CurrenciesController`, `UnitsOfMeasurementController`, `AuditLogsController` (paged, filterable by table/action, expandable old/new JSON values).
- **Known API-driven UI limitations at this point (by design, not bugs)**:
  - Users/Roles had no `GET by id` endpoint on the API yet (only paged list + create/update/delete) — later closed, see [identity.md](identity.md).
  - No API endpoint to read a role's currently-assigned permissions, so `Roles/Permissions` could only Assign/Revoke blind (no checkbox state).
- Validated: `dotnet build Sugentra.ERP.sln` — 0 warnings/errors across all 4 projects (Api, Migrator, Tests, UI). Smoke-started `Sugentra.ERP.UI` standalone — unauthenticated request to `/` correctly redirects to `/Account/Login`, no startup exceptions.
- **Not yet done at this point:** end-to-end login test against a running API instance; transparent JWT refresh when the access token expires mid-session (currently relies on the 14-day sliding cookie only, no refresh-token exchange wired into `ApiClient` yet); no automated UI tests.

## Standard list-page toolbar pattern: `_ShowEntries` + search/Filter dropdown/Add New
Established while polishing `GoodsReceipts/Index.cshtml` — this is now the **default toolbar layout for any new/updated list page**, not a one-off for that module.

- **Layout**: one `d-flex justify-content-between align-items-center flex-wrap gap-2` row inside the card, directly under `card-header`. Left side is `@await Html.PartialAsync("_ShowEntries", ...)` (its own `<form>`); right side is a second, sibling `<form method="get">` containing, in order: keyword search input → Filter dropdown button → (optional) "Add New" link. The two `<form>`s must be **siblings**, never nested — `_ShowEntries` renders its own `<form>` for the page-size selector, and nesting forms produces invalid HTML that breaks submission.
- **Filter trigger is a real `<button>`, not a bare icon**: `<button type="button" class="btn btn-sm btn-outline-primary position-relative" data-bs-toggle="dropdown" data-bs-auto-close="outside" aria-expanded="@(hasAdvancedFilter ? "true" : "false")"><i class="ri ri-filter-3-line me-1"></i>Filter</button>`. Button style never changes on active filter (stays `btn-outline-primary`) — instead a small red dot badge (`position-absolute top-0 start-100 translate-middle p-1 bg-danger border border-light rounded-circle`, `visually-hidden` text) renders conditionally on `hasAdvancedFilter` to signal an active filter.
  - **Lesson learned**: this vendor icon set's `ri-filter-3-fill` and `ri-filter-3-line` (in `iconify-icons.css`) have **identical SVG data** — swapping between them for an "active" state is a no-op, don't rely on it. Likewise swapping to `text-primary` on the icon did nothing visible since `btn-outline-primary`'s own text color is already primary-colored — a genuinely distinct visual cue (badge dot, background fill, etc.) is required.
  - The dropdown toggle and its `.dropdown-menu` must be **direct siblings inside the same `.dropdown` wrapper div** (Bootstrap/Popper position the menu relative to its sibling toggle) — splitting them into separate wrapper divs breaks positioning.
- **Filter panel content = a `.dropdown-menu` (`dropdown-menu-end w-px-500 p-0`) wrapping a `card mb-0 shadow-none`** with `card-header` ("Filter" title), `card-body` (`row g-2`, each field in `col-md-6 mb-2` with a `form-label mb-1 small` label — free-text/reference fields as `form-control form-control-sm`, enums as `form-select form-select-sm`, dates as flatpickr-bound `form-control form-control-sm` — see below), and `card-footer d-flex justify-content-end gap-2` with a Clear link (`asp-action="Index"`, resets all filters) + submit button, both `btn btn-sm btn-filter-action`.
- **Date filter fields use flatpickr directly on a plain `form-control form-control-sm`** — no `input-group`/calendar-icon-toggle wrapper (that pattern from Create/Edit forms was tried and explicitly rejected here as unnecessary chrome for a filter panel). Requires `@section VendorStyles { <link rel="stylesheet" href="~/vendor/libs/flatpickr/flatpickr.css" /> }` / `@section VendorScripts { <script src="~/vendor/libs/flatpickr/flatpickr.js"></script> }` at the top of the view, and an init script that just does `document.querySelectorAll('.your-date-flatpickr').forEach(el => flatpickr(el, { dateFormat: 'Y-m-d', allowInput: true, appendTo: document.body }))`.
  - **Critical lesson (jQuery timing bug)**: this view already had a pre-existing **plain inline `<script>`** tag (non-`@section`) at the bottom of the body for a delete-modal helper. Appending jQuery-style flatpickr init code (`$(function () {...})`) into that same plain script threw `ReferenceError: $ is not defined`, because plain inline `<script>` tags in the view body execute during initial parsing — **before** the shared layout's bottom-of-body jQuery `<script>` tag has loaded. Content inside `@section Scripts { }` runs after jQuery loads and is safe to use `$` in; anything left as a bare inline `<script>` in the view body must be vanilla JS only (`document.querySelectorAll`/`addEventListener`/`DOMContentLoaded`), never jQuery.
- **`_ShowEntries.cshtml` (shared partial, `Views/Shared/_ShowEntries.cshtml`) labels are `mb-0 small`** ("Show"/"entries") to match the `form-select-sm` page-size dropdown next to them — plain `mb-0` labels look oversized next to a `-sm` control. The page-size `<select>` itself needed a scoped CSS override (`.show-entries select.form-select-sm { min-height: calc(1.375em + 0.4rem + calc(1px * 2)) !important; padding-block: 0.2rem !important; }` in `site.css`) since the app-wide `.form-select-sm` min-height rule (tuned for normal-size label text elsewhere) reads as oversized once the adjacent labels are shrunk to `small`.
- This whole pattern (toolbar row structure, Filter-button+badge, card-based dropdown filter panel, plain flatpickr inputs, `_ShowEntries` small labels) is the **new baseline** — apply it to any list page filter redesign going forward instead of re-deriving it from scratch.
- **Root cause fix**: the earlier field-height fix only worked on Users because `.form-control-sm` sizing was scoped to `.filter-form .form-control-sm` — other list pages' filter `<form>`s never had the `filter-form` class. Fixed by dropping the `.filter-form` requirement — the rule now targets plain `.form-control-sm`/`.form-select-sm`/`.btn-sm` app-wide.
- **Add button follow-up**: `Roles`/`Currencies`/`Items`/`PriceLists`/`UnitsOfMeasurement`/`BusinessPartners`/`BillOfMaterials`/`Menus`/`Modules` had their header "Add X" button at plain `btn btn-primary` (larger) size — Users' was the only one already `btn btn-sm btn-primary`. All nine changed to `btn-sm` to match.
- Validated: `dotnet build src/Sugentra.ERP.UI/Sugentra.ERP.UI.csproj` / `dotnet build Sugentra.ERP.sln` (0 warnings/errors) after each batch of edits.
- **Not yet done**: Export/Import/Refresh header buttons were only added to `Users/Index.cshtml` (see [identity.md](identity.md)) — not replicated to the other list pages. No company logo had actually been uploaded yet at the end of this session (`Setting_CompanyProfile.LogoUrl` likely null), so the login page fell back to text-only until one is set via Settings → Company Profile.
