## Sample data seed for empty Master Data/Settings lists
Roles/Permissions/Users/Menus/Modules already had seed data from earlier phases; `Currencies`, `UnitsOfMeasurement`, `BusinessPartners`, `Items`, `PriceLists`, and `BillOfMaterials` (+ their component lines) had none, so those list pages rendered empty.

- New script: `Scripts/MasterData/0006_Seed_SampleMasterData.sql` — deliberately **one self-contained script** covering both `Setting_Currencies`/`Setting_UnitsOfMeasurement` (Settings tables) and `MasterData_BusinessPartners`/`Items`/`PriceLists`/`BillOfMaterials`/`BillOfMaterialItems`, instead of splitting the Settings/MasterData inserts into separate per-folder scripts. Reason: DbUp's `WithScriptsEmbeddedInAssembly` sorts all embedded scripts alphabetically by full resource name across every folder combined (`Identity` < `MasterData` < `Settings`), so a *new* `MasterData/000X_...` seed script would run before a same-batch *new* `Settings/002X_...` seed script even though the MasterData rows (Items/PriceLists) have hard FK dependencies on the Currency/UoM rows — keeping everything in one script sidesteps that cross-folder ordering risk entirely (statements execute top-to-bottom within a script regardless of folder).
- Data: 4 currencies (USD/IDR/EUR/SGD), 6 units (KG/MT/PCS/CBM/SET/ROLL), 6 business partners (aliases only, no "PT ..." company names — e.g. "Rimba Rotan", "Anggun Kriya", "Global Rattan Trading"), 6 items (raw/semi-finished/finished rattan goods), 5 price list entries, 2 BOMs with 4 component lines total. All inserts guarded with `WHERE NOT EXISTS` so re-running the migrator is idempotent.

**3. `MasterData_BusinessPartnerContacts` (new, one-to-many):** `Id`, `BusinessPartnerId` (FK), `ContactType` (`Phone`/`WhatsApp`/`Fax`/`Email`), `ContactName` (PIC name), `Value`, `IsPrimary`, + standard audit columns.

**Rationale (why child tables, not more columns on the core table):** a partner can have several addresses (office ≠ billing ≠ shipping) and several contacts (multiple PICs, multiple phone numbers) — modeling these as repeatable columns (`Address2`, `Phone2`...) doesn't scale past a fixed count. **Why NPWP fields stay on the core table (not a child table):** a business partner has exactly one tax identity (one NPWP or one NIK), so it's a 1:1 attribute of the partner, not a repeatable one — no need for a child table there.

## Bugfix: `GetAllAsync()` on header+lines UseCases returned raw entities without lines
`PriceListsController`/`Index.cshtml` and `BillOfMaterialsController`/`Index.cshtml` threw a `NullReferenceException` on `@priceList.Lines.Count` / `@bom.Lines.Count` — root cause: `PriceListUseCase.GetAllAsync()` and `BillOfMaterialUseCase.GetAllAsync()` returned `IReadOnlyList<PriceListHeader>`/`IReadOnlyList<BillOfMaterial>` (bare entities, no `Lines`) instead of the `...Response` DTO, so the UI's Razor model (typed as `PriceListResponse`/`BillOfMaterialResponse`) deserialized `Lines` as `null`.
- Fix: both `GetAllAsync()` methods now project every header through the existing `ToResponseAsync` helper (`await Task.WhenAll(headers.Select(ToResponseAsync))`), returning `IReadOnlyList<XxxResponse>` with `Lines` populated, same as `GetByIdAsync` already did.
- **Lesson for future header+lines UseCases** (BOM/PriceList pattern): `GetAllAsync()` must return the same Response DTO as `GetByIdAsync()`/`CreateAsync()`/`UpdateAsync()` — returning the bare entity list is a trap that only breaks once the UI's Index view touches `.Lines`.
- Validated: `dotnet build Sugentra.ERP.sln` — 0 Warnings/Errors, `dotnet test` — `ModuleBoundaryTests` 1/1 passing.

## Server-side paging for BusinessPartner/Item/PriceList lists + DB-level "one primary per type" constraint
Closed the two remaining tech-debt items called out earlier ("no paging on BusinessPartner/Item/PriceList list endpoints", "no DB-level constraint enforcing at most one primary address/contact per type"). Implemented additively — no existing UseCase/Repository/CrudUseCase logic touched.
